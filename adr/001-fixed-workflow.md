# ADR-001: фиксированная цепочка для J1/J2

| Поле | Значение |
|---|---|
| Статус | принят |
| Дата | 22 ноября 2026 |
| Авторы | Команда Labestra |
| Связано | [design doc, разделы 4–6](../design_doc.md#4-архитектура-решения); [workflow](../docs/WORKFLOW.md) |

## Контекст

Labestra ищет в фиксированной коллекции и готовит черновик с основаниями.
J1 завершается выбором корпуса, J2 получает корпус заранее. Бюджеты на запуск:
20 действий, 10 LLM-вызовов, 5 поисковых, 300 секунд, 100k входных/30k выходных токенов в live v2 (15k выхода в fixture).
Последовательность должна воспроизводиться при ошибках, изменении вводных и отмене.

## Рассмотренные варианты

| Вариант | Качество | Задержка | Стоимость | Сложность |
|---|---|---|---|---|
| Фиксированная цепочка | Проверяемые ID и корпус; заданный порядок действий | Обычно 2 действия J1 и 3 J2 без повторов | 1 генерация на обычный путь; справочный тариф DeepSeek задан, фактический счёт прокси не подтверждён | Обычные функции и один Runtime |
| Свободный агентный цикл | Может менять запросы и исследовать неоднозначность; улучшение не доказано | Число шагов зависит от решений модели | Потенциально больше вызовов в тех же квотах | Нужны правила выбора инструментов, дополнительные сценарии и оценка |
| Только поиск и извлечение | Дословные фрагменты без смыслового синтеза | Локальный поиск без генерации | Нет LLM-расхода | Реализуется общим runner и используется для сравнения |

## Решение

Выбрать фиксированную цепочку. Python управляет переходами, модель предлагает
план/уточнение и структурированный черновик. Поиск J1 требует подтверждения,
J2 читает только заданный корпус. Общий Runtime резервирует ресурсы до действия
и считает каждую попытку. Переходы и доступные инструменты определяются кодом.

## Последствия

- **Плюсы.** Порядок действий и основания проверяемы; общий Runtime учитывает
  бюджет до каждого действия. Технические сценарии повторяются без API.
- **Минусы.** Нет автоматического расширения поиска, свободного выбора инструментов,
  пользовательской памяти и восстановления прерванной сессии. Неудачный search_query
  ограничивает доступные основания.
- **Что нужно сделать.** Сохранять единые контракты и Runtime в runner; ограничивать
  repair одним, временные повторы двумя. При неизвестном usage прекращать новые
  платные вызовы. Оценка поведения проверяется сценариями, смысловые оценки
  ответов хранятся отдельно.
- **Условия пересмотра.** Если разбор ошибок покажет систематическую нехватку
  фиксированной последовательности, провести сравнение с адаптивным циклом на
  тех же входах. Перейти к нему только при улучшении заранее выбранной метрики
  качества без превышения 20 шагов, 300 с и 0,10 USD на задание.
