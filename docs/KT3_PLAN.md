# Labestra: минимальный план КТ3 на четырёх человек

**Команда:** 1 — Аркаша (данные), 2 — Макс (поиск), 3 — Олег (workflow/LLM), 4 — Сабухи (runner/оценивание).

**Дедлайн курса: 23 ноября 2026, 23:59. Внутренняя готовность: 22 ноября вечером.**

## 1. Что делаем

**Одно локальное Python-приложение с командным интерфейсом.** Оно ищет по сохранённым научным источникам, читает фрагменты и формирует ответ с основаниями. Сравниваем его с поиском и ручным ответом без LLM.

Одна папка проекта, один процесс, одна модель, фиксированная коллекция, результаты в JSON/JSONL. SQLite допускается как готовый механизм поиска FTS5, но отдельный сервер базы не нужен.

Путь пользователя: вопрос → уточнение при необходимости → подтверждённый план → поиск → выбор корпуса → чтение фрагментов → черновик → проверка человеком. Выбор и подтверждение можно сделать через терминал. Для J2 в оценочных заданиях корпус задан заранее, чтобы baseline и система сравнивались на одинаковых материалах.

Это учебный прототип. **Не делаем** web, регистрацию, роли, управление участниками/задачами, отдельные Core/Agent-сервисы, внутренний HTTP API, Docker-инфраструктуру, live-каталоги, память пользователя, векторную БД и dashboard.

## 2. Что обязательно по курсу и замечаниям

| Требование | Самое простое достаточное исполнение | Доказательство |
|---|---|---|
| Настоящий научный eval | Снимки, вопросы, gold ID, обязательные выводы и основания | Файлы данных, проверяемые ID и хеши |
| Независимая разметка | Два человека на одной подвыборке, затем согласование | Исходные метки, совпадения и κ до обсуждения |
| Baseline без LLM | BM25/поиск по словам + ручной ответ | Ответы и время человека |
| Одинаковый вход | Один runner с выбором `baseline`/`system` | Одна инструкция и одинаковая схема результата |
| Воспроизводимость | Конфигурация, версии, модель, промпты, параметры и данные | Manifest каждого прогона |
| Контракты инструментов | Python-функции с типизированными аргументами, ошибками, тайм-аутами и квотами | Спецификация и проверки |
| Шаги и остановка | Конечный счётчик, тайм-аут и лимит стоимости/токенов | Проверка исчерпания шагов |
| 5–7 многошаговых сценариев | Делаем 6, включая повтор и отмену | События, конечное состояние, pass/fail |
| Память на своём уровне | Состояние текущего запуска + сохранённые результаты | Описание контекста, переполнения и перезапуска |
| Измеренный baseline | Качество, длительность, стоимость и человеческое время | Таблица с исходными результатами |
| Один ADR | Фиксированный pipeline вместо свободного агентного цикла | Одна страница по шаблону ADR |
| Design doc и оформление | Один обновляемый файл, план наблюдаемости, PR/MR и форма | Diff и комплект сдачи |

Курс прямо допускает фиксированную цепочку генераций или многошаговый диалог вместо агентного цикла. **Модель не обязана сама выбирать инструменты.** Наш код управляет шагами; смена вопроса, ошибки, повтор и отмена обрабатываются этим кодом.

Преподаватель отдельно потребовал досдать корпус, gold и разметку. Исправления текста и успешные технические проверки не заменяют научные данные.

## 3. Общий договор перед работой — до двух часов

Вместе фиксируем:

- Версию Python и зависимости.
- Вход задания: ID, question, английский search_query, класс, часть набора, ID коллекции/корпуса и ограничения. Gold в решающий вариант не попадает.
- Формат источника/фрагмента: стабильный ID, происхождение, точный текст, координаты и хеш.
- Выход: статус, ответ, claims, evidence, ограничения, причина остановки, usage, время и стоимость.
- Событие: run/step ID, функция, аргументы/результат, ошибка, время и ресурсы.
- Ошибку: код, сообщение и можно ли повторить.

Все модули — обычные функции, импортируемые в runner. Сетевые API внутри приложения не создаём. Участник 4 сохраняет общий формат, остальные реализуют адаптер к нему. Для начала используем одну настоящую статью и два dev-задания.

Подготовленная структура проекта (реализация поиска, workflow и runner ещё предстоит):

```text
labestra/
  search.py       # поиск и чтение фрагментов
  workflow.py     # фиксированная последовательность и LLM
  runner.py       # baseline/system, измерения и сохранение
  schemas.py      # общие форматы
prompts/
data/             # источники, фрагменты и манифест
eval/            # в репозитории: видимые входы и правила проверки
runs/             # сохранённые результаты без секретов
adr/
design_doc.md
README.md
```

Gold доступен только оцениванию, holdout хранится приватно. Каталоги, начальные типы и сигнатуры созданы. data/search/workflow/runner — только заглушки; валидация, тесты, научные данные и результаты ещё предстоят.

### Решения по стыкам, 19 ноября

- Сабухи загружает данные через функции Макса и создаёт LocalSearch(sources=..., fragments=..., config=config["search"], collection_id=...).
- Аркаша готовит исходный question и отдельный английский search_query для обоих вариантов. Автоперевода/LLM-переписывания запроса нет; для clarify/refuse запрос может быть пустым.
- Фильтры не нужны: filters={}; непустые — invalid_input. Ограничение корпусом обязательно.
- Общий учёт и логирование — обёртка Сабухи; Олег передаёт ей LLM usage, Макс не дублирует общий бюджет.
- Макс возвращает упорядоченную выдачу, Сабухи сохраняет её до выбора пользователя. Первая выдача — для Recall/Precision, выбранный Corpus — отдельно.
- B0: Макс — поиск/чтение, Сабухи — показ/ввод/время. Пилот на 3 dev-кейсах предложен на 20 ноября 17:00–18:00 МСК, команда ещё подтверждает время.

- Сигнатуры search_sources/search_fragments/read_fragments сохраняются. Макс обеспечивает отдельный тайм-аут поиска (30 с из config), Сабухи — общий deadline и учёт; Олег — timeout LLM-адаптера.
- ToolError.tool_call_id уже необязателен при создании (пустая строка); обёртка Сабухи добавляет реальный ID перед сохранением события.
- Каждый делает личную feature-ветку от origin/checkpoint-3 и отдельный PR в checkpoint-3. Общие сигнатуры не меняем без согласования.

Полный договор и формат ошибок — [раздел 3.5 подробного плана](KT3_PLAN_DETAILED.md).

## 4. Аркаша (участник 1) — научные данные и первичный gold

**Цель:** подготовить проверяемую контрольную работу для программы, а не список возможных вопросов.

1. Выбрать узкую тему из RAG/дообучения, по которой команда может читать статьи.
2. Для поиска собрать примерно 30–40 записей с метаданными/аннотациями, включая отвлекающие. Для анализа сохранить доступные тексты примерно 6–10 работ. Основной пул J1 должен быть больше 20, иначе Recall@20 при возврате всего пула тривиален.
3. Сохранить DOI/OpenAlex ID, происхождение, доступность, точный текст и хеш. Не задавать вопрос о недоступном разделе.
4. Подготовить 6 dev-заданий, 24 видимых (12 J1, 12 J2) и 12 отложенных. Это рабочий объём, не обязательное число курса; если объём меняется, обосновать по классам до оценки. Вопросы одного эксперимента и перефразы не пересекают части.
5. J1: зафиксировать пул кандидатов, релевантные ID и ожидаемые действия/уточнения; без фильтра года. J2: корпус, обязательные атомарные выводы, условия и точные основания.
6. Подготовить пары claim/fragment с supports/contradicts/uncertain и инструкцию оценки. Не использовать ответ модели как gold.
7. Передать участнику 2 **без первичных меток** 8 выбранных видимых кейсов (4 J1, 4 J2) для независимой разметки тех же объектов.
8. Сохранить первичные метки, получить вторые, затем считать согласие и разбирать расхождения. Согласованный gold хранить отдельно от исходных меток.
9. Записать фактический состав, доли классов, источники, group split и хеши в manifest. Holdout не раскрывать до КТ4.
10. После прогонов независимо оценивать результаты вместе с 2. Обновить разделы о данных, наборе и разметке.

**Передаёт:** источники, задания, gold, инструкцию, исходные/согласованные метки и manifest.

**Готово, когда:** на любом видимом J1/J2 можно посчитать научные метрики по реальным файлам. Неразрешимые ID, отсутствующие эталоны и пустые корпуса не принимаются как готовый набор.

## 5. Макс (участник 2) — поиск, baseline и независимая разметка

**Цель:** простой детерминированный поиск, общий для обоих вариантов.

1. Реализовать загрузку материалов 1 и стабильные ID фрагментов. Выбрать простой готовый разбор текста; универсальный PDF/OCR не делать.
2. Реализовать BM25/FTS5. Сохранить tokenizer, параметры, правила разбиения и сортировку равных результатов по ID. Для старта веса title/abstract/body — 1/1/1; настройки выбираются только на dev.
3. Поиск возвращает до 20 статей; поиск фрагментов — до 10, до 3 на источник. Сохранять ранжирование до человеческого отбора. Чтение возвращает точный текст, а не пересказ.
4. Проверять неизвестные ID и принадлежность выбранному корпусу. Не реализовывать роли пользователей и права проектов: их нет в локальном учебном варианте.
5. Передать функции `search_sources`, `search_fragments`, `read_fragments` участникам 3/4. У функций — понятные ошибки, квоты и тайм-ауты.
6. Вместе с 4 подключить B0: поиск → человек читает → вводит ответ/claims/evidence в тот же runner. LLM в B0 не используется.
7. На трёх dev-кейсах вместе с 3/4 определить численный лимит ручной сессии. Сохранить правило учёта времени/незавершённых заданий до сравнения; не ставить человеку машинные 5 минут.
8. Независимо разметить 8 кейсов от 1, не видя его меток. Отдать исходные метки до обсуждения; потом проверить расхождения и итоговый gold.
9. Совместно с 1 оценивать смысл ответов, которых сами не составляли. Считать собственные метрики поиска программно, не через LLM-судью.

**Передаёт:** поиск и чтение, конфигурацию, вторую разметку, регламент B0.

**Готово, когда:** одинаковый запрос/корпус дают одинаковую выдачу, ID разрешаются в текст, gold сравнивается кодом; пустая выдача и k<20 обработаны явно.

## 6. Олег (участник 3) — фиксированный процесс и LLM

**Цель:** получить проверяемый ответ через небольшую управляемую цепочку.

1. Проверить модель в Yandex AI Studio, сохранить точный ID, параметры, тариф и дату. Ключ хранить вне Git.
2. Реализовать один адаптер LLM с usage, временем, обработкой ошибок и тайм-аутом. Скрытые автоматические повторы SDK отключить или включить в общий учёт.
3. Сделать промпты уточнения/плана и ответа. Фиксировать их полный текст/хеш.
4. Реализовать фиксированный путь: уточнение при необходимости → план → подтверждение → поиск → выбор/фиксация корпуса → чтение → генерация структурированного черновика. J2 на eval получает заранее заданный корпус.
5. Проверять JSON, claim/evidence ID и принадлежность корпусу; один запрос исправления формата допустим в общих квотах. При нехватке данных возвращать insufficient_evidence.
6. Подключить общий счётчик и обёртку Сабухи для шагов/времени/денег, передавать ей LLM usage; независимый бюджет workflow не создавать. Максимумы проекта: 20 действий, 10 LLM-вызовов, 5 поисковых, 300 с, 100k/15k токенов, $0.50 либо явно настроенный эквивалент. Любой retry считается действием; проверка до вызова. Числа — проектная конфигурация, не требования преподавателя к точным значениям.
7. До двух повторов временной ошибки в квотах; постоянная ошибка завершает запуск с причиной. Не выдумывать результат упавшего инструмента.
8. Поддержать отмену и изменение вводных между шагами. Поздний ответ после отмены не публикуется как completed.
9. Описать состав и ограничение контекста, сокращение лишних фрагментов/истории. Отдельная память пользователя и автоматическое продолжение после перезапуска не нужны.
10. С участником 4 написать один ADR: фиксированная цепочка вместо свободного агента — почему достаточна для J1/J2, какие ограничения и когда нужен цикл.
11. На оценке вместе с 4 составлять ручные B0-ответы **до получения доступа к gold**. Собственные ответы не оценивать.

**Передаёт:** workflow, адаптер, промпты, конфигурацию, события, описание инструментов и контекста.

**Готово, когда:** реальный вопрос проходит путь до ответа с существующими основаниями; ошибки/бюджет/отмена останавливают цепочку; нет скрытых неучтённых вызовов.

## 7. Сабухи (участник 4) — общий runner, файлы результатов и проверки

**Цель:** запускать оба варианта одинаково и собирать проверяемые результаты.

1. Создать общий формат `schemas.py` и runner с выбором baseline/system. Сделать минимальный терминальный ввод подтверждения, выбора и ручного ответа. Web/API-сервер не писать.
2. Создать общий учёт запуска и обёртку SearchTools для обоих вариантов; сохранять каждый запуск в отдельную папку: вход, настройки, predictions, события, токены/время/стоимость, причины остановки. Manifest содержит код/изменения, данные, модель, промпты, параметры, тариф и режим live/fixture.
3. Сохранение сделать идемпотентным: ключ+хеш тела; повтор возвращает прежний результат, другое тело с тем же ключом — conflict. Хватит одного процесса и файловой записи с временным файлом/атомарной заменой. Распределённые транзакции не нужны.
4. Сохранять отмену и не разрешать позднюю публикацию completed. Порядок событий фиксировать. Перезапуск сохраняет результаты; автоматический resume не обещать.
5. Написать шесть сценариев из следующего раздела; управляемые ошибки отделить от реальных LLM-прогонов.
6. Программно считать ID-поиск, формат, целостность evidence, шаги, длительность и цену. Семантические метрики загружать из меток 1/2. Исходные ошибки не исключать.
7. Посчитать согласие 1/2 до согласования, с числом объектов и распределением меток; при неопределённой κ указать причину. Не подставлять готовые метки семинара.
8. Запустить видимый набор после заморозки. Один полный реальный прогон — основной результат КТ3; повторы важнейших сценариев и дополнительные полные прогоны допустимы по бюджету. Число повторов фиксируется заранее, лучший результат не выбирается. Разброс полного набора и holdout обязательны к КТ4.
9. Составлять ручные B0-ответы вместе с 3 без gold. После сдачи ответов можно заниматься агрегированием меток, но не оценивать собственные ответы.
10. Собрать отчёт: качество поиска, качество научного ответа и технические проверки — отдельно; время машины/человека, стоимость, ошибки. Acceptance всегда рядом с количеством claims, Correctness и Gold Coverage.
11. Сделать README, сверить его чистым запуском коллегой, собрать design doc из разделов участников. Финальную демонстрацию и документы проверяют все.

**Передаёт:** runner, сохранение, шесть проверок, программные метрики, отчёт и README.

**Готово, когда:** одна инструкция воспроизводит запуск обоих вариантов и проверки; каждое число связано с результатом, а технический fixture не выдаётся за научное качество.

## 8. Шесть сценариев — все обязательные случаи

| ID | Последовательность | Проверка |
|---|---|---|
| S1 | Поиск → полученные ID → чтение → генерация | Следующий шаг использует результат предыдущего; ссылки существуют |
| S2 | Успешный шаг → временная ошибка → повтор → продолжение/отказ | Повторы ограничены, данные и причина сохранены |
| S3 | Шаги до специально уменьшенного лимита | Остановка именно по шагам, новых вызовов нет |
| S4 | Вопрос/план → пользователь меняет условия → новый поиск/ответ | Новые условия учтены, старый результат не выдан за новый |
| S5 | Запись результата → имитация потери ответа → повтор | Один файл/результат, прежний ID; конфликт другого тела |
| S6 | Запуск → отмена → поздний ответ | Статус cancelled, нет completed-публикации и следующих действий |

Противоречие источников проверяется в научных J2-кейсах отдельно. Для КТ3 курс требует противоречие **или** изменение вводных; не добавляем седьмую техническую цепочку только ради количества.

Для каждой проверки нужны вход, исходное состояние, ожидаемые действия/запреты и конечное состояние. Не требуем единственного списка вызовов там, где порядок независимых шагов несущественен.

## 10. Что положить в сдачу

- Код, зависимости, пример настроек без ключей, README.
- Коллекцию, фрагменты, видимые задания, доступные оцениванию gold и manifest; holdout остаётся приватным.
- Исходные метки двух людей, согласие и согласованный gold.
- Конфигурацию поиска, численный лимит B0, ответы и время человека.
- Реальные system-результаты с моделью, промптами, usage, ценой и временем.
- Шесть цепочек с pass/fail и событиями.
- Один `design_doc.md` по актуальному шаблону и один ADR с альтернативами.
- PR/MR с преподавателем в ревьюерах и ссылку в форму.

Отдельный dashboard, production, backend авторизации и универсальная агентная платформа не являются условиями этой сдачи. Полноту научного набора нельзя заменять инфраструктурой или красивым текстом. При небольшом объёме не заявлять точность на всём домене: обосновать классы и явно показать ограничения.
