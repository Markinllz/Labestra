# Labestra — подробный план выполнения КТ3

**Команда:** 1 — Аркаша (данные), 2 — Макс (поиск), 3 — Олег (workflow/LLM), 4 — Сабухи (runner/оценивание).

**Дедлайн курса — 23 ноября 2026, 23:59. Внутренняя готовность — 22 ноября вечером.**

## 1. Что делаем и что считаем готовым

Один локальный Python-проект. Поиск по сохранённым научным материалам, фиксированная цепочка подготовки ответа через одну LLM, ссылки на точные фрагменты, проверка человеком. Без сайта, регистрации, ролей, серверного API, отдельных сервисов, контейнеров и свободного агентного цикла.

Два пользовательских пути:

- **J1:** вопрос → уточнение/план → подтверждение → поиск → выбор источников → сохранённый корпус.
- **J2:** вопрос + заданный корпус → поиск/чтение фрагментов → ответ с claims/evidence → проверка человеком.

Сравниваем **B0** (тот же поиск + ручной ответ без LLM) и **system** (тот же поиск + фиксированный LLM-workflow). Одни входы и программа запуска; разные способы подготовки ответа. Никакого дополнительного web-поиска для одного варианта во время сравнения.

Сдаём код и инструкцию, реальные источники и задания, эталоны, независимую разметку, измеренный B0/system, шесть сценариев, один ADR и один обновлённый design doc.

**Каркас уже есть.** В `schemas.py` начальные типы, остальные модули содержат заглушки. Ни поиск, ни LLM, ни runner, ни проверка данных пока не реализованы. `.gitkeep` обозначает пустую папку, а не готовый результат. Справка CLI работает, научный запуск — ещё нет.

## 3. Первые два часа: договориться, чтобы не переделывать

### 3.1 Запустить существующий каркас

Каждый из корня репозитория:

```bash

source .venv/bin/activate
python -m labestra --help
```

Python 3.11+. Если `.venv` уже существует, достаточно активации. Сейчас внешних зависимостей нет. Нужные зависимости добавляем только по мере реализации и фиксируем версии перед оценкой. `pip install -e .` не является настроенным способом установки каркаса; используем запуск из корня.

Сначала команда проверяет общий локальный diff и согласует базовую версию, от которой будут работать все. Отправка и фиксация изменений выполняются владельцем отдельно; наличие файлов в локальной папке ещё не означает, что коллеги получили их через Git.

### 3.2 Зафиксировать один способ взаимодействия

Все части вызывают друг друга как Python-функции:

```text
runner.run_case(case, tools, config, run_id, variant)
    baseline → поиск + ручной ввод
    system   → workflow.run_system(case, tools, config, run_id)
                  tools.search_sources(...)
                  tools.search_fragments(...)
                  tools.read_fragments(...)
```

Внутренние HTTP-сервисы, очереди, интерфейсы плагинов и универсальный агентный фреймворк не создаём. Достаточно существующего `SearchTools`.

На текущих заглушках можно договориться о вызовах, но нельзя оценивать качество. Вместо настоящих инструментов в тесте разрешён маленький объект с теми же методами и заданными ответами; такой тест маркируется fixture.

### 3.5 Решения по вопросам Макса 7–12 — зафиксированы 19 ноября

**7. Создание поиска.** Сабухи в runner читает конфигурацию, вызывает загрузчики Макса из data.py и создаёт один LocalSearch. Конструктор получает sources, fragments, config["search"] и collection_id. Макс реализует загрузчики и построение индекса, но не запуск всего приложения.

```python
tools = LocalSearch(
    sources=sources,
    fragments=fragments,
    config=config["search"],
    collection_id=config["collection_id"],
)
```

Путь к файлам — config["paths"]["data_dir"], ID коллекции — config["collection_id"], он должен совпасть с manifest/Case. На КТ3 одна фиксированная коллекция; Corpus J2 передаётся в методы отдельно. Пока конструктор и загрузчики — заглушки.

**8. Языки и запрос.** Аркаша готовит в задании question и отдельный search_query на английском. Это обычный вход обоих вариантов, зафиксированный до оценки, не gold. Макс ищет по search_query; Олег получает для модели исходный вопрос и английские фрагменты. Автоперевод и LLM-переформулирование поискового запроса не реализуем. Для обычного CLI английскую фразу вводит пользователь отдельно. Если вопрос требует уточнения/отказа, search_query может быть пустым; для реального поиска он обязателен. Нельзя незаметно подставить русский question вместо отсутствующего запроса.

В B0 начальная поисковая фраза та же. Разрешённые регламентом дополнительные ручные запросы пишутся отдельными событиями и входят во время. Основные Recall/Precision считаем по первой выдаче одинакового исходного запроса, не выбираем лучшую из последующих. После изменения вводных новая версия вопроса и search_query явно подаются вместе.

**9. Фильтры.** Для КТ3 filters={} — без фильтра года и других пользовательских метаданных. Непустой filters возвращает invalid_input, а не игнорируется. Принадлежность выбранному корпусу проверяется всегда. Аркаша не включает проверку года в обязательный набор; исторические описания таких сценариев не расширяют текущий контракт.

**10. Бюджеты и ошибки.** Сабухи создаёт общий учёт запуска и обёртку SearchTools. Он передаёт её Олегу, а B0 вызывает тот же объект. Обёртка проверяет отмену, шаги, время и квоты перед вызовом и пишет события/расход после. Олег отдаёт в общий учёт реальные LLM-попытки и usage; не ведём два независимых общих бюджета. Макс отвечает за корректность и конечность одного вызова, включая локальный тайм-аут из search-конфигурации; общий счётчик у себя не дублирует.

Ошибки передаются через ToolFailure(ToolError): code, message, retryable, tool_call_id. Макс может оставить tool_call_id пустым, общая обёртка привязывает фактический ID вызова перед логированием. Коды: invalid_input, not_found, outside_corpus, timeout, io_error. Пустой поиск без совпадений — нормальный пустой список. NotImplementedError остаётся только признаком незаполненного каркаса.

**11. Выдача до отбора.** Макс возвращает Source в порядке ранжирования, без сортировки по gold и ручного отсева. Сабухи сразу сохраняет query, filters, collection_id, настройки и исходные упорядоченные ID. Поле RunResult.retrieved_source_ids содержит первую выдачу; все дополнительные запросы — в events. Corpus хранит выбранные source_ids отдельно; его ID записывается в corpus_revision_id. Ручной отбор не перезаписывает исходное ранжирование.

**12. B0 и пилот.** Макс предоставляет поиск/чтение, Сабухи — показ фрагментов, ввод ответа, отсчёт времени и сохранение через общий runner. Предлагаемое время совместной проверки: **20 ноября, 17:00–18:00 МСК**, требует подтверждения командой. На 3 dev-кейсах проверяем поиск, ответ по фрагментам и недостаток оснований. После пилота фиксируем конфигурацию и численный лимит ручной сессии до оценки.

### 3.6 Уточнение сигнатур, тайм-аутов и PR — 19 ноября

**Три метода поиска не меняем.**

```python
search_sources(query: str, filters: dict[str, str], collection_id: str) -> list[Source]
search_fragments(query: str, corpus: Corpus) -> list[Fragment]
read_fragments(fragment_ids: list[str], corpus: Corpus) -> list[Fragment]
```

Конструктор LocalSearch уже объявлен отдельно; model/gold/состояние runner в методы не добавляем. Нужные ограничения отдельного поиска передаются при создании через config["search"]. Изменение общей сигнатуры согласуется до слияния PR, а не делается молча в одной ветке.

**Один вызов и весь запуск — разные ограничения.** Макс обеспечивает тайм-аут одного вызова поиска/чтения из config["search"]["timeout_seconds"] (сейчас 30 с) и сообщает timeout через ToolFailure; бесконечного ожидания быть не должно. Сабухи контролирует общий deadline, шаги и квоты и назначает ID вызова. Перед стартом проверяет остаток времени и не начинает вызов, если зарезервированный тайм-аут уже не помещается в него. Повторы выполняются по общей политике и считаются отдельно; внутри поиска независимые ретраи не скрываем. Для LLM фактический timeout реализует Олег в адаптере, общий учёт остаётся тем же. Проверка времени только после возврата зависшего вызова не обеспечивает тайм-аут.

**ToolError уже исправлен.** В коммите 45625f2 поле tool_call_id имеет значение по умолчанию "". Макс создаёт ToolError(code, message, retryable) и поднимает ToolFailure. Обёртка Сабухи привязывает фактический ID перед сохранением события. Так как ToolError — frozen dataclass, для добавления ID используется dataclasses.replace, а не присваивание полю. Пустой ID допустим до обёртки, но не в сохранённом событии выполненного вызова.


Сейчас эти файлы отсутствуют. Создаём их после появления содержимого, не заполняем пустыми JSONL ради видимости готовности. Holdout лучше физически держать вне общей папки у участника 1; `.gitignore` защищает от случайного коммита, но не от чтения коллегами с диска.

### 4.2 Источник и фрагмент

Используем поля существующих Source и Fragment:

- Source: source_id, title, origin, availability, external_id, url, snapshot_path, sha256.
- Fragment: fragment_id, source_id, text, location, snapshot_sha256.

`external_id` — нормализованный DOI или ID OpenAlex. `source_id` — стабильный внутренний ID. Одна работа не должна становиться двумя документами из-за разных внешних ID: при необходимости хранить таблицу алиасов как метаданные, а не считать дубль ещё одной релевантной статьёй.

`availability` различает metadata, abstract и full_text. Если сохранена только аннотация, вопросы по результатам отсутствующего раздела не задаём как ответимые. Фрагмент дословно входит в текстовый снимок. Хеш снимка — SHA-256 его байтов. Хеш очищенного текста не называем хешем оригинального PDF.

### 4.3 Case — только вход решающему варианту

Поля: case_id, phase (J1/J2), split, category, group_id, question, search_query, collection_id, corpus_revision_id, history и рабочие лимиты.

Для J2 заранее задана редакция корпуса. Для J1 фиксирован пул поиска, а результат отбора сохраняется отдельно. `group_id` объединяет перефразы и вопросы об одном эксперименте: такая группа не делится между dev/visible/holdout.

Вход может содержать доступный текст источника — это нормально. Он не должен содержать правильные ID, обязательные выводы, исходные метки или ответы проверяющих.

### 4.4 Gold — отдельный эталон

Для J1:

- case_id;
- candidate_source_ids — фиксированный доступный пул;
- relevant_source_ids — нормализованный эталонный список;
- expected_action — search/clarify/refuse;
- rationale — почему работы релевантны/почему требуется уточнение.

Для J2:

- case_id и corpus_revision_id;
- expected_action — answer/insufficient_evidence/clarify;
- required_claims: gold_claim_id, text, conditions;
- evidence для каждого вывода: fragment_id и relation.

Для двойной разметки:

- annotator_id, case_id, object_id, label, rationale, rubric_version;
- object_id у двух людей обозначает **один и тот же объект**: source_id, ожидаемое действие либо пару claim_id/fragment_id;
- исходные метки не переписываются после обсуждения; согласованная версия — отдельный файл.

Для финального свободного ответа gold не обязан перечислять все допустимые дополнительные выводы. Каждый дополнительный вывод проверяется по корпусу. Нельзя автоматически назвать его ошибкой только потому, что его нет в списке обязательных выводов.

### 4.5 Manifest

Участник 1 сохраняет: версию набора, дату заморозки, состав/количество кейсов по классам и частям, происхождение, group split, правила нормализации/нарезки и хеши файлов. Полный список вопросов должен существовать, а не быть обещанием собрать его позже.

Манифест для solver не раскрывает gold. Для holdout достаточно подтвердить размер, хранителя и хеш приватной версии, не публикуя вопросы до КТ4.

Сохранять usage из ответа. Если usage/цена неизвестны, не писать 0; вернуть неизвестность/ошибку измерения. Продолжать платные действия без известного предела цены нельзя.

### Шаг 2. Создать минимальные промпты

- План/уточнение: вопрос, известные условия, короткий план или конкретный вопрос пользователю; доступные данные и ограничения.
- Анализ: актуальный вопрос, корпус, точные фрагменты с ID, схема ответа, требование не выдумывать содержание и сохранять противоречия/условия.

Gold в промпт не передаётся. Текст статьи — данные, а не новая инструкция. Не требуем от модели абсолютной научной истины; она готовит черновик по доступному тексту.

Выход модели: answer, claims с evidence, limitations, evidence_status. run_id, измерения, технический status и stop_reason устанавливает программа, а не доверяет им как факту из текста модели.

### Шаг 3. Реализовать фиксированный J1

1. Прочитать вопрос и условия; при неоднозначности вернуть needs_clarification и уточняющий текст.
2. Подготовить план и ждать подтверждения. До подтверждения search не вызывается.
3. Выполнить поиск, сохранить ranked source IDs до отбора.
4. Получить выбор пользователя или явно заданное действие тестового сценария; сохранить Corpus с новым ID и выбранными источниками.
5. Вернуть результат J1, не изображая его научным ответом J2.

Для оценочного J1 поиск и ранжирование измеряются до ручного отсева. В сценарных тестах подтверждение/выбор можно подавать как заранее заданные реплики; это должно быть видно в mode и описании проверки.

### Шаг 4. Реализовать фиксированный J2

1. Проверить заданный Corpus и вопрос.
2. Найти подходящие фрагменты только в этом корпусе, прочитать их точный текст.
3. Собрать ограниченный контекст.
4. Вызвать модель для структурированного черновика.
5. Проверить JSON, допустимые relation, уникальность claim_id, существование evidence и принадлежность корпусу.
6. Допустить не более одного запроса исправления формата в общем бюджете; не бесконечный цикл.
7. Вернуть RunResult для сохранения. Недостаток данных обозначить evidence_status=insufficient_evidence; это не обязательно техническая ошибка запуска.

Не пытаться программно доказать смысл поддержки по наличию ID. Существование проверяет код, корректность и entailment — человек.

### Шаг 5. Лимиты и контекст

Сабухи реализует общий учёт и обёртку инструментов в runner; Олег пользуется ими и передаёт фактические попытки/usage модели. Ниже описано поведение общего механизма, не второй независимый счётчик внутри workflow.

Проектные пределы: 20 действий, 10 LLM-вызовов, 5 поисковых, 300 с, 100k входных/15k выходных токенов и выбранная денежная квота. Действие — реальный вызов модели или инструмента; повтор считается, внутренняя обёртка того же вызова отдельно не считается.

Перед каждым действием:

1. Проверить отмену и истечение времени.
2. Проверить max_steps и квоту типа действия.
3. Для LLM оценить вход, ограничить выход и зарезервировать верхнюю цену.
4. Если ресурсов недостаточно — остановить до вызова.
5. После вызова записать фактический расход, результат или ошибку.

При API-timeout счётчик попыток увеличен; неизвестное фактическое списание не выдаётся за ноль. Документировать такое ограничение отдельно и сверять биллинг, если провайдер не вернул usage.

В контекст попадают инструкции/схема, вопрос и нужная история, основания с ID и нужные наблюдения. Окно одного вызова и суммарный лимит запуска — разные величины. Начальные квоты из design doc проверить на выбранной модели; при переполнении убирать повторные/нерелевантные результаты и лишнюю историю, сохраняя вопрос и происхождение evidence. Если нужные основания не помещаются, явно сузить задачу/указать ограничение.

### Шаг 6. Ошибки, изменение вопроса и отмена

На временную ошибку инструмента — до 2 повторов в общих квотах. На неизвестный ID или неправильный корпус повтор с теми же аргументами не помогает. Постоянный сбой завершает задачу с причиной либо явно ограниченным частичным результатом.

Изменение вопроса в диалоге означает новый актуальный запрос и новый план/ответ; старый результат не переименовывается. Отмена должна быть проверена перед следующим действием и после возврата внешнего запроса, до передачи completed на сохранение. Учебная проверка отмены не требует сервера: можно использовать callback/заданное событие теста или флаг в локальном состоянии, который runner меняет между шагами/во время ожидающего вызова.

Подставить маленький SearchTools и LLM-адаптер с заданными ответами. Проверить: подтверждение до поиска, реальные ID в следующем шаге, один repair JSON, конечные retries, остановку при max_steps, нехватке денег/токенов и отмене. Отдельно сделать хотя бы один реальный dev-вызов. Успех тестового адаптера не выдаётся за live-результат.

## 8. Сабухи (участник 4) — подробная инструкция

### Шаг 1. CLI и config

Сохранить простую точку входа и текущую форму аргументов:

```bash
python -m labestra --variant baseline --cases eval/visible/tasks.jsonl --config configs/default.json
python -m labestra --variant system --cases eval/visible/tasks.jsonl --config configs/default.json
```

**Сейчас это будущие рабочие команды:** каркас только разбирает параметры и сообщает об отсутствии реализации. Не добавлять подкоманды/HTTP API без необходимости.

Сабухи в CLI читает config, загружает sources/fragments/corpora/cases через data.py и создаёт LocalSearch по 3.5. Runtime-парсер dataclass добавляется участником 2; при чтении nested Limits/Claim/Evidence нельзя оставить обычные dict там, где код ждёт объект.

Зафиксировать приоритет конфигурации/лимитов, валюту и path resolution. Пути конфигурации — относительно явно выбранного корня, не случайного текущего каталога. Ключи берутся отдельно и не попадают в сериализуемую config прогонов.

### Шаг 2. Один runner для двух вариантов

`run_case` создаёт run_id, записывает вход и начало времени, затем:

- baseline: использует тот же search_query, показывает поиск/фрагменты, принимает ручной ответ и evidence;
- system: вызывает `run_system` с теми же данными и config;
- оба пути приводятся к RunResult, проходят структурную проверку и сохраняются одинаково.

Интерактивный B0 не пишется в отдельном ноутбуке. Для заполнения claims/evidence достаточно терминального ввода или редактируемого JSON-файла, открытого в рамках **той же сессии runner**; время редактирования учитывается. Не требуется строить для этого GUI.

B0 не получает выход модели или gold. Для разных вариантов сохраняются отдельные результаты; начальная коллекция/корпус совпадает, состояние одной сессии не загрязняет другую.

### Шаг 3. Сохранение

На каждый run_id:

```text
manifest.json       # код, данные, модель, промпты, параметры, режим
input.json          # только solver-вход
config.json         # без секретов
prediction.json     # RunResult
corpus.json         # если J1 создал корпус
events.jsonl       # реальные действия и ошибки
evaluation.json    # позже: программные метрики и ссылки на ручные метки
```

Папки в примере создаются при реальном запуске, не заранее с пустыми результатами. Usage и время можно держать внутри prediction, отдельные файлы необязательны.

Manifest: версия кода (коммит и отметка/хеш локальных изменений), зависимости, версия/хеши данных, точная модель, тексты/хеши промптов, temperature/seed при поддержке, тариф и дата, variant и live/fixture. Ошибку не заменять вымышленным успешным prediction.

Сохранение атомарное через временный файл и замену. Idempotency key и хеш тела фиксируются; одинаковый ключ/тело возвращают прежний результат, другое тело — conflict. Для одного процесса не нужны распределённые блокировки, база или транзакционный сервис. Удаление/перезапись уже сохранённого результата не считается повтором.

Отмена сохраняется так, чтобы позднее completed не заменило cancelled. После перезапуска старые результаты читаются; automatic resume не нужен.

### Шаг 4. Проверки результата

Проверять status/variant/mode, структуру claims/evidence, допустимые relation, ID, выбранный корпус, измерения и stop_reason. Отделять:

- техническое завершение;
- достаточность evidence;
- решение человека о принятии.

Dataclass сам не обеспечивает эти инварианты. `cost=None` означает неизвестно, не бесплатно; `human_active_seconds=None` означает не измерено, не ноль.

### Шаг 5. Метрики

| Что считаем | Источник | Как |
|---|---|---|
| Recall@20 | Исходная выдача + gold ID | Релевантные в первых 20 / все релевантные в фиксированном пуле |
| Precision@k | Первые k результатов + gold | Релевантные / k; k≤20, фактическое k опубликовано |
| Key Claim Count | Модель + ручная атомизация всего текста | Оба количества рядом |
| Correctness | Метки 1/2 | Верные атомарные утверждения / все утверждения |
| Gold Coverage | Обязательные выводы + метки | Верно отражённые обязательные / все обязательные |
| Evidence Entailment | Метки на claim/fragment | Верные отношения / все проверенные связи |
| Evidence Coverage | Проверяемые утверждения и ссылки | Существующие основания нужного корпуса / все фактические утверждения |
| Acceptance | Независимый чек-лист | Принятые / все запланированные ответимые J2 |
| Шаги и ошибки | Events и конечное состояние | По каждому S1–S6; нарушения отдельно |
| Ресурсы | Usage и часы | Токены, вызовы, время машины/человека, стоимость |

M1 считается по первой выдаче одинакового search_query. Для исходной выдачи нельзя сначала убрать нерелевантные работы, а затем выбрать top-20. Если k<20 — это Precision@k, а не Precision@20. Для пустой выдачи при непустом gold Recall=0; Precision для пустого результата записать как 0 по принятому правилу проекта и добавить empty_result; формулу с делением на k=0 не применять. При пустом gold Recall=N/A, expected clarify/refuse оценивается отдельно.

Ошибки и пустые ответы на ответимый J2 остаются в знаменателе принятия и не повышают качество искусственно. Для кейса с ошибкой фиксировать нулевое покрытие и failure, отдельно публиковать частоту ошибок; не усреднять только успешные ответы. Отношения при отсутствии связей — N/A, покрытие оснований фактического ответа — 0. Ожидаемый отказ не штрафуется как пропуск обязательного вывода, если ответимости нет.

Стоимость считать по фактическим токенам в единицах тарифа. Baseline не тратит LLM-токены, но тратит время человека. Учитывать чтение/составление/проверку, а время независимой исследовательской разметки отдельно не выдавать за продуктовый latency.

Сначала отчёт по кейсам и классам, затем агрегаты с ясными знаменателями. На небольшом наборе точность оценок ограничена; не обещать качество всего научного домена. Статистические интервалы полезны, но сложный статистический стенд не должен блокировать обязательный корректный прогон.

### Шаг 6. Согласие разметчиков

Взять исходные метки 1/2 на тех же object_id. Посчитать совпадения и Cohen’s κ отдельно для действий, релевантности и отношений. Сохранить число объектов, распределение меток, таблицу расхождений. Если κ не определена из-за одного класса, указать это, а не подставлять 1.

Не считать согласие по меткам после обсуждения. Не использовать синтетические labels семинара вместо своей разметки.

### Шаг 7. Оценочный прогон

1. Убедиться в наличии manifest, полного состава, gold и разметки; заморозить config.
2. 3/4 выполняют ручной B0 без gold; один человек не решает последовательно один и тот же вопрос в двух режимах.
3. Выполнить system на видимых заданиях с реальной моделью.
4. Выполнить S1–S6 с заданными ошибками и отмеченным fixture-режимом.
5. Передать обезличенные ответы 1/2 для независимой оценки.
6. Агрегировать метки и программные измерения; каждый результат сохранить, не выбирать лучший.

Для КТ3 достаточно одного полного реального прогона зафиксированного варианта; дополнительные повторы возможны по бюджету, число указывается заранее. К КТ4 нужен полный набор с holdout и разбросом. Исправление кода/промпта после прогона — новая версия и повтор затронутой оценки, не переименование старого результата.

## 9. Шесть многошаговых сценариев: точная приёмка

### S1. Зависимость шагов

Дать вопрос и коллекцию с известными ID. После подтверждения поиск возвращает список, чтение получает ID из него, ответ использует существующие evidence. Проверить порядок событий, аргументы чтения и принадлежность оснований корпусу. Придуманный ID или поиск до подтверждения — fail.

### S2. Ошибка в середине

После одного успешного действия заставить следующий инструмент дважды вернуть временную ошибку, затем успех. Проверить не более двух повторов, отдельный учёт попыток, продолжение с сохранёнными данными. Отдельно проверить постоянную ошибку: явная остановка, не бесконечные повторы. Не заменять это проверкой одной функции «ловит Exception».

### S3. Бюджет шагов

Уменьшить только max_steps, остальные лимиты оставить достаточными. Довести процесс до следующего запрещённого действия. Проверить budget_exceeded, причину max_steps, отсутствие этого вызова и сохранение частичных данных. Если первым сработал тайм-аут/деньги, тест шагового лимита не пройден как задумано.

### S4. Изменение вводных

После плана пользователь меняет тему/условие вопроса. Новое действие использует актуальные вводные, старый план не выполняется без учёта изменения. Ответ и история относятся к правильной версии вопроса. Можно задавать реплики через тестовый callback, полноценный чат-сервер не нужен.

Противоречие источников дополнительно проверяется в научном J2, но отдельная седьмая техническая цепочка не обязательна: курс требует противоречие **или** изменение вводных.

### S5. Повтор записи

Сохранить результат, имитировать потерю подтверждения, отправить тот же ключ и тело. Проверить один результат и прежний ID. Затем другое тело с тем же ключом — conflict, без молчаливой перезаписи.

### S6. Отмена

Начать внешний вызов, установить отмену до его окончания и вернуть поздний ответ. Проверить cancelled, запрет следующего действия и отсутствие completed-публикации. Проверяется фактическое сохранённое состояние, а не только фраза «отменено» в терминале.

Каждый сценарий содержит начальное состояние, входы, заданные ошибки/реплики и конкретные проверки. Допустимые независимые действия не обязаны иметь единственный жёсткий порядок. Все шесть технических результатов публикуются отдельно от научных метрик.

После каждого соединения проверить один dev-кейс целиком. Зависимости:

1. Источники 1 → загрузка/поиск 2.
2. ID/типы 2 → workflow 3.
3. Case/RunResult → runner 4, его каркас пишется параллельно.
4. Согласованные данные/gold → официальная оценка.

До готовности модуля коллеги использовать маленькую тестовую подстановку с теми же сигнатурами. Это способ разрабатывать параллельно, а не способ заменить реальный научный результат.

**Барьер:** пока нет настоящих источников, полного состава, gold и исходных независимых меток, официальный отчёт о качестве не готов. Если к вечеру 19 ноября нет сквозного пути, прекращаем добавление функций; все помогают соединить один J1/J2. UI, новые модели и инфраструктура не добавляются.

## 11. Финальные документы и сдача

### Design doc

Один `design_doc.md`, по актуальному шаблону. Не создавать новый design doc на каждую КТ. Заполняем фактическое:

- 1/2: узкий контракт, без обещаний многопользовательского сервиса.
- 3: цели и реальные измерения, не выдавать потолки за средние расходы.
- 4/5: реально работающие функции, workflow, ошибки и квоты.
- 6: локальное состояние, контекст, переполнение, отсутствие resume/долгой памяти.
- 7: реальные ссылки на файлы, размеры, split, gold и согласие.
- 8: числа B0/system и честный вывод; необязательные усложнения можно не реализовывать.
- 9: поля событий и короткий план готового трейсинга к КТ4; dashboard сейчас не обязателен.
- 10/11: реальные ограничения/неудачи и оставшиеся открытые вопросы.
- 12–14: план, ресурсы и ссылки на созданные артефакты.

### ADR

Один файл `adr/001-fixed-workflow.md` по шаблону курса. Статус, дата, авторы; контекст с ограничениями; минимум фиксированная цепочка и свободный цикл как варианты; качество/задержка/стоимость; решение; последствия; условия пересмотра. Не заявлять измеренный выигрыш, если его не мерили.

### README

Реальная установка и команды, порядок подготовки/проверки данных, переменные окружения без значений ключей, запуск обоих вариантов и сценариев, место результатов. Удалить прежнее сообщение «каркас», когда функции действительно заработают. Не оставлять инструкции к несуществующим файлам.

### Чистый запуск

Участник, не писавший инструкцию, получает чистую копию, ставит зависимости, подключает свой ключ для live и выполняет команды. Технические тесты должны работать без платных вызовов. Сохранённые реальные прогоны доступны ревьюеру, даже если API временно недоступен; записанный прогон явно обозначается, не выдаётся за новый live.

### Список готовности

- [ ] Есть реальные снимки/фрагменты и проверяемые ID/хеши.
- [ ] Весь научный набор и эталоны существуют, части/группы зафиксированы.
- [ ] Два исходных файла разметки, согласие до обсуждения и согласованный gold сохранены.
- [ ] Поиск и регламент B0 зафиксированы до оценки.
- [ ] Одна программа запускает B0/system на одинаковых входах.
- [ ] Реальный LLM-прогон сохраняет модель, промпты, параметры, usage, стоимость и время.
- [ ] Есть результаты S1–S6; они не названы научным качеством.
- [ ] Ошибки и непроверенные ответы не исключены из отчёта.
- [ ] Качество, полнота, entailment и принятие оценены независимо от автора.
- [ ] Design doc, один ADR и README соответствуют коду.
- [ ] Из репозитория исключены ключи, приватный holdout и неподходящие для публикации материалы.

Последние внешние действия выполняет команда после проверки; этот план ничего автоматически не коммитит и не публикует.

## 12. На что не тратить время

Не делать серверную авторизацию, роли, задачи участников, отдельные Core/Agent-контейнеры, HTTP API между модулями, web, агентный фреймворк, vector DB, fine-tuning, память пользователя, live-каталоги и production-мониторинг.

Не добавлять статистические/архитектурные инструменты только ради количества. Нельзя сокращать реальные эталоны, независимую разметку, общий runner, измеренный B0, обязательные сценарии и сохранение ресурсов. Качество сдачи — в проверяемости, а не числе файлов.
