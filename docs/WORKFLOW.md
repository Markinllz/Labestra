# Участник 3 — workflow, модель и промпты

Дата: 22 ноября 2026. Подготовлено для части Олега.

**Готова локальная реализация с проверками без модели.** Она использует публичные
данные Аркаши и поиск Макса. Реальные вызовы API, измерение научного качества и B0
в эту проверку не входят. `runner.py` остаётся задачей участника 4.

**Обновление 23 ноября.** Runtime и WorkflowServices подключены в общем runner.
Для Qwen добавлен ChatModel (Chat Completions API); YandexModel сохранён для
Text Generation API. Запуск/локальная конфигурация/скрытый ввод ключа/ZIP описаны
в README. Ниже сохранено описание исходной части участника 3; пункты про будущий
runner теперь реализованы. При усечении сохраняется известный usage; при неизвестном
usage останавливается вся сессия. Авторская отметка accept не является независимой оценкой.

## Что запустить

Из корня проекта, Python 3.11+ с SQLite FTS5; сторонних зависимостей нет:

```bash
python3 -m unittest discover -s tests -v
python3 -m labestra.workflow_demo
```

Вторая команда создаёт новую папку `runs/local/workflow-fixture-.../` и печатает
путь. Для своего пути: `python3 -m labestra.workflow_demo --output /tmp/my-new-run`.
Каталог должен быть новым: пример не перезаписывает предыдущий результат.

В каждом из шести dev-кейсов сохраняются `input.json`, `config.json`, `result.json`,
`events.jsonl`, `corpora.json` и `manifest.json`. В корне — `summary.json`.
Данные и поиск настоящие, ответы модели и действия человека — явно заданные
технические fixtures. Вызовов сети — 0, стоимость — 0 RUB, токены синтетические.
В J2 fixture возвращает цитату для проверки ссылки и явно сообщает, что научного
ответа нет; `insufficient_evidence` здесь не является оценкой качества модели.

## Подключение к runner Сабухи

Один Runtime создаётся **runner для всего запуска**. В workflow второго счётчика нет.
Референсная реализация вынесена отдельно, чтобы её мог использовать также B0.
Не оборачивать уже обёрнутый SearchTools и не дублировать учёт в другом слое.

```python
from dataclasses import replace
from labestra.schemas import Limits
from labestra.workflow_runtime import Runtime
from labestra.workflow import WorkflowServices, run_system

# config загружен из JSON, raw_search — LocalSearch Макса, corpora — реестр Аркаши.
limits = Limits(**config['limits'])
case = replace(case, limits=limits)
runtime = Runtime(run_id, limits, mode='fixture', cancelled=cancel_flag.is_set)
tools = runtime.wrap_search(raw_search)
services = WorkflowServices(runtime, fixture_model, corpora, interaction_callback)
result = run_system(case, tools, config, run_id, services=services)
# runner сохраняет result, runtime.events и services.created_corpora.
# Перед финальной публикацией runner снова проверяет отмену.
```

Сохранены четыре исходных аргумента `run_system`; добавлен keyword-only `services`.
Без него функция явно сообщает об отсутствии интеграции. В сериализуемую config
не кладутся ключ, callbacks, объекты модели или runtime. Конструктор live Runtime
требует тариф, дату его проверки и совпадение валют. ID, параметры, код и данные
фиксирует manifest runner; пример показывает нужные поля и хеши изменённых файлов.

Контракт `interaction_callback(event, payload) -> dict | None`:

| Событие/действие | Ответ |
|---|---|
| `confirm_plan` | `{"action":"confirm"}`; иначе `needs_clarification` |
| `select_sources` | `{"action":"select","source_ids":[...]}` — непустое подмножество выдачи |
| Любая граница шага | `{"action":"cancel"}` |
| Изменение вводных | `{"action":"revise","question":"...","search_query":"..."}` |
| Изменение J2-корпуса | То же, плюс известный runner `corpus_revision_id` |
| Нет действия на обычной границе | `None` |

Есть границы `start_revision`, `before_llm`, `after_llm`, `before_search`,
`before_read`, `before_publish`. При изменении вопроса старые промежуточные данные
сбрасываются, общий расход сохраняется, уточнение/поиск выполняются заново.
Максимум 20 изменений вводных; это дополнительная защита от бесконечного диалога.
Для отмены во время API-вызова runner передаёт неблокирующий `cancelled` callback.

J1 возвращает первичное ранжирование в `retrieved_source_ids` и новый корпус
отдельно в `created_corpora`, без научного ответа J2. Обёртка сохраняет результат
поиска до отбора. J2 разрешает только переданный ID корпуса и использует
неизменённый английский `search_query`. Gold и категории эталонных действий не
передаются модели. Функция не открывает файлы gold/holdout; `split=holdout`
отклоняется для текущего этапа КТ3.

## Ограничения, ошибки и контекст

* 20 действий, 10 вызовов LLM, 5 поисковых, 5 чтений, 300 секунд,
  100 000 входных / 15 000 выходных токенов. Денежный предел задаётся явно
  в той же валюте, что и тариф; для fixture это 0 RUB, для live пока не выбран.
* Реальная попытка LLM/инструмента, включая retry и repair, — одно действие.
  UI, валидация и запись события не увеличивают счётчик действий.
* Перед вызовом резервируются шаг, квота, timeout, вход/максимальный выход и
  верхняя стоимость. Недостаток ресурсов останавливает запуск **до** вызова.
* До двух повторов временной ошибки. Неизвестный ID/корпус, отмена и постоянная
  ошибка не повторяются. Скрытых повторов SDK нет: используется стандартный REST.
* Если расход запроса неизвестен, usage/стоимость становятся `null`, запуск
  останавливается с `usage_unknown`. Даже временная ошибка не оправдывает ещё
  одну платную попытку без известного остатка. После HTTP-ошибки текущий адаптер
  консервативно считает биллинг неизвестным; нужны сверка и решение человека.
* LLM исполняется в daemon-потоке; ожидание ограничено deadline и проверяет отмену.
  Поздний ответ не меняет результат/события и не публикуется. Запрос у провайдера
  может продолжить вычисление: остановка ожидания не обещает отмену списания.
  Поиск SQLite выполняется на исходном потоке и использует deadline Макса.
* JSON разбирается строго: дубликаты ключей, NaN, лишние технические поля,
  повторные claim_id и неизвестные/повторные evidence ID отклоняются.
  Ровно один дополнительный запрос регенерации формата допустим на весь запуск.
* Evidence должен находиться не только в корпусе, но и среди фрагментов,
  действительно прочитанных и включённых в контекст данного ответа.
  Смысловая поддержка claim кодом не доказывается.

По умолчанию один запрос ограничен 8000 входными и 1500 выходными единицами при
конфигурационном окне 16000. Для локальной консервативной оценки используется
число UTF-8-байтов + запас на оформление сообщений; это **не измерение токенов**.
Перед live надо проверить верхнюю границу и размер окна на выбранном токенизаторе;
флаг `token_bound_verified` по умолчанию false блокирует живые вызовы workflow.
Из API берётся реальный usage; превышение зарезервированной границы останавливает
цепочку. Для моделей с отдельной тарификацией reasoning нужен иной проверенный тариф.

Текущий вопрос не обрезается. В J1 лишняя история удаляется при переполнении.
J2 использует актуальный самодостаточный вопрос и точные фрагменты без старой
истории. Целые фрагменты добавляются в порядке поиска, непоместившиеся ID
записываются как excluded и в limitations. Текст внутри фрагмента не режется.
Если не помещается ни один — `insufficient_evidence`. Runtime-состояние живёт
только в процессе; сохранённые JSON не означают автоматический resume.
